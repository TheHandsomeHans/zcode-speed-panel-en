# Key Rules and Pitfall Details

Required reading before changing code. Each entry is a real incident that occurred in this project, including symptoms and root causes; violating them leads to hard-to-detect functional failures.

## 1. `$()` is getElementById, throws immediately if not found

`src/main.ts`'s `$()` looks up elements via `document.getElementById`; it throws `missing #xxx` when the element does not exist.
**An error thrown mid-module-load = total frontend paralysis with no feedback**: metrics/mode event listeners are never registered, manifesting as all-zero values and mode-switching failure; listeners attached before the crash point still work, giving a "half-broken" illusion.
- Incident: the top bar was a `<header>` tag with no id, `$("header")` blew up immediately (fixed: `#app-header`).
- Rule: new HTML nodes must carry the correct id; after modifying main.ts you must run `npx tsc --noEmit` + browser mock mode (`npm run dev` then open localhost:1420) to verify rendering.

## 2. Tauri 2 permission whitelist: unapproved window APIs are all rejected

Frontend calls to window core APIs (minimize / toggleMaximize / startDragging...) must be explicitly approved in `src-tauri/capabilities/default.json` under `permissions` (e.g. `core:window:allow-minimize`), otherwise the call is rejected.
- Incident: the — / ▢ buttons had no response — missing permission, and `.catch(() => {})` silently swallowed the error (fixed: added permission).
- Rule: add permissions in sync when introducing new window API calls; **do not mask failures with empty catch blocks** — at least `console.warn`. In dev you can open F12 to see permission errors. Custom commands (`#[tauri::command]` + `generate_handler!`) are not subject to this restriction.

## 3. Real-time speed consistency calibration: calibration and display must share the same cleaning pipeline

The numerator of the byte-to-token coefficient must come from exactly the same cleaning pipeline used for display (`build_rows` integrated over the invocation interval); systematic deductions (noise floor / disk mirror / burst rejection) can only be cancelled out by the coefficient.
- Incident: calibration used uncleaned total bytes (~900-1400 B/token) while display used the cleaned pipeline (true value ~350-550 B/token); the coefficient was inflated 2-3x, real-time readings showed only 1/5 of the true value (~10 t/s vs 40-50).
- Rule: when modifying liveio sampling/cleaning logic, calibration integral and display magnitude inside `measure()` must share the same source; the synthetic end-to-end tests (`synthetic_call_converges_to_true_tps` etc.) are guards and must remain passing.

## 4. Per-tick cleaning must not clamp to non-negative (negative ticks cancel out)

Disk flush and IO counters are misaligned: a single tick may show "file grew 60KB but process only wrote 20KB". This tick must be recorded as a negative value, relying on interval integration (`integrate`) to cancel with neighbouring positive ticks; only apply `max(0, ·)` at the window aggregate.
- Incident: an older version applied `max(0, delta-disk)` per tick; misaligned bytes were permanently lost, roughly half of invocation readings collapsed to ~130 B/token.
- Related: the adaptive noise floor must be capped (`FLOOR_CAP_BYTES=2KB`), otherwise quantiles are poisoned by streaming increments during sustained streaming, deducting the process's own output.

## 5. Calibration sample admission: silent invocations pollute the coefficient

A substantial fraction of invocations are "pipeline silent" — the UI pipeline sees almost no incremental bytes during generation, everything flushes at the completion instant. For such invocations the pipeline integral divided by tokens can be as low as ~7 B/token; admitting them drags down the median coefficient and inflates real-time readings.
- Rule: samples must pass `cal_sample` admission (eff >= 300 tokens, clean >= 20% of raw, B/token in [100, 6000] and not hitting clamps); rejected samples are discarded entirely (log `skipped=true`). Admitted samples are handed to the **recent-weighted median + AR(1) shrinkage estimator** (`cal_estimate`: 16-sample window, half-life 3, two-pass pruning [0.4, 2.5], then one log-space shrinkage step toward the newest sample with ρ=0.3 and ratio clamped to [0.5, 2] — single-sample impact ≤ ×1.23, an outlier only pulls one tick, and the first sample after a magnitude jump leads) to produce the coefficient; the queue is pre-seeded with the 600 prior and linearly shrinks toward the prior when the window has fewer than 3 samples — a single anomalous sample cannot dominate the coefficient at cold start.
- Noise floor magnitude and structure (second calibration round, 2026-09-24): on this machine, 262 real samples have B/token p25~p75 = 466~740; log-space lag-1 autocorrelation ≈ 0.50, lag-2 ≈ 0.27 ≈ ρ² (**pure AR(1)** — consecutive calls share content style); any coefficient predictor's per-call error floor is ≈ 20% median — real-time reading deviations of 20–30% are normal fluctuation, don't rashly retune because of this. B/token is negatively correlated with true speed (r ≈ -0.3~-0.5; fast calls render in larger batches, fewer bytes per token) but **cannot be exploited**: back-solving requires the unknown current-call speed. Changing the estimator must pass the benchmark: real-sample replay `python scripts/cal_bench.py` (compare tables before/after the change, no regression allowed) + liveio tests `benchmark_*` (steady-state AR(1) / jump convergence / bounded outlier drag). Replayed-and-rejected approaches: per-model calibration (two rounds of validation: GLM-5.3 and Flash sample distributions are consistent; deepseek-v4-flash samples med≈221 but n=3 — the magnitude difference is speed-driven and the sample is too thin to support an independent queue), two-parameter bytes ≈ a×token + c×duration model (per-call error med 48%~90%), EWMA / global shrinkage / larger mean window (half-life 6) / eff weighting / AR1 out-of-bounds skip — no gain or worse, don't retry rashly.

## 6. Debug log is the first-hand data for investigation

`~/.zcode/speed-panel-debug.jsonl` (JSONL append, 8MB rotation keeping one generation `.jsonl.1`, rotated files older than 7 days auto-cleaned at startup) records four event types:
- `tick`: display value `tps`, source `src` (io/window/idle), startup-phase `start`, cleaned pipeline byte rate `pipe`, active coefficient `bpt`, curve tail bucket, count of processes reaching streaming magnitude in window `npids`;
- `call`: invocation completion truth (`eff`/`gen_ms`/`true_tps`);
- `cal`: calibration reconciliation (`true_tps` vs `pred_tps`, `raw_kb`/`clean_kb`, `bpt_sample`/`bpt_now`, `skipped`, attribution diagnosis `attr_pid`/`top_pid`, cross-process guard diagnosis `others_kb` — other processes' raw bytes in window; when their share relative to the attributing process is large, the sample is rejected);
- `cal_reset`: recalibration (`reason`=manual/auto, coefficient before/after `bpt_old`/`bpt_new`; auto also records the triggering round average `round_avg` and 5-round baseline `base_avg` — check here for "why did the coefficient suddenly revert to prior").

Real-time accuracy evaluation metric: `pred_tps / true_tps` -> 1.00 is accurate. Use `python scripts/live_vs_true.py` for one-click reconciliation (invocations with >=300 tokens that entered calibration are qualifying samples). Diagnose real-time reading issues here first, do not guess.

## 7. Compile-time coupling between examples and src

`src-tauri/examples/{dump,verify}.rs` directly include `metrics.rs`/`liveio.rs` via `#[path]`. When changing the public API of these two modules (struct fields, function signatures), examples must also be updated, otherwise `cargo test`/`cargo build --examples` fails.

## 8. WebView2 native `<select>` dropdown follows system theme, unreadable in dark UI

The native select's **dropdown overlay** is rendered by WebView2 according to system theme: when system is light, the overlay is white-background, and options inherit the page's grey text style, making them nearly invisible in a dark interface; in practice `:root { color-scheme: dark }` and explicit option coloring both have no effect in the WebView2 overlay. Native checkbox/radio behave the same (boxes drawn in system light theme) — in dark UI all must be custom-drawn.
- Incident: the floating-window style dropdown "couldn't see the text" (fixed: fully replaced with custom-drawn `.dropdown`/`.dropdown-list`, same dark overlay style as the right-click menu); desktop pet "always show last round avg speed" checkbox misaligned — `#float-menu button { all: unset; display: block }` is an "ID+element" selector (specificity (1,0,1)), the single-ID `#float-menu-pet-last { display: flex }` (1,0,0) could not override it; after flex failed the checkbox degenerated to inline zero-dimension (fixed: changed to double-ID selector `#float-menu #float-menu-pet-last`, same weighting for the hide rule).
- Rule: this project's UI must custom-draw all dropdowns/checkboxes, no new native `<select>`/`<input type=checkbox>`; when changing layout for a control inside a compound selector rule that has `all: unset`, the overriding selector's specificity must be higher (double ID or `#id button#id` form); when adding new top-bar interactive components, also add them to enableDrag's drag and double-click maximize exclusion selectors (`button, select, input, .dropdown`), otherwise window drag/maximize is falsely triggered (using a `<button>` to host the new control naturally matches).

## 9. Start/stop gating must use the `completed` field of the message row, not model_usage completion rows

Invocation start/stop determination uses the usage library message table assistant message row: **the row is submitted at the invocation start instant (<=200ms), the row's data `time.completed` is backfilled at the completion instant (also backfilled on cancel/error)**. The `model_usage` row only records `status='completed'` — cancelled/error invocations (97+119 rows observed in the actual database) **never have a completion row**; judging stop via completion rows gets stuck in "generating" until the 10-minute fallback; also it does not distinguish sessions, so the first invocation in a new conversation is not visible until the first completion row lands (long invocations can take several minutes).
- Incident: old criterion "latest assistant creation time > latest completed invocation's completed_at, limited to the latest completed invocation's session" — after user cancelled generation the panel kept showing "generating + estimated value" for up to 10 minutes; new conversations showed no response throughout.
- Query constraint: the message table has **no standalone index on time_created** (global `ORDER BY time_created DESC` measured ~200ms per query, 700ms polling is unsustainable) — must first take `session.time_updated` descending for the first few sessions, then use the `(session_id, time_created)` composite index to query the latest assistant row per session.
- Stop fallback (`liveio::stale_stop`): `completed` backflush can lag seconds to minutes, during which the gate stays open and the window fallback keeps showing "generating + approx last round speed" (2026-09-17 user report "conversation stopped but still showing generating, slowly decreasing"). Once the anchor appears and the cleaning stream cuts off for >15s (`SILENT_STOP_MS`) force stop is applied; if the anchor is not established (pipeline-silent invocation) it is unaffected. Pure function test `stale_stop_after_silent_window` guards this.
- Guards: `inflight_from_rows` (metrics.rs) is the gating pure-function unit test (zombie rows/multi-session/expired); `awaiting_hint` (liveio.rs) guards the startup-phase hint window. Both tests must remain passing when modifying gating-related code.

## 10. mac platform differences (silently fails if Windows parameters are copied directly)

The platform primitives for real-time speed measurement live in `liveio::platform` (win/mac/stub three cfgs); cleaning/calibration parameters are platform-parameterized by `CleanParams`. The following differences were all discovered through real-world testing; required reading before cross-platform liveio changes:

- **mac burst is the signal itself, BURST_TICK_BYTES must be disabled**: on Windows a single tick >100KB is request-body upload (should be rejected as a whole tick); on mac streaming itself is single-tick burst form (measured single-tick +225KB~1.5MB is normal, alternating 0,0,0,+large blocks), reusing the 100KB threshold throws away **all** streaming signal as bursts, real-time reading is always 0. mac side takes `u64::MAX` to disable.
- **files deduction is a directional backfire on mac**: the disk-write deduction on Windows (tracked file growth subtracted from write bytes) must be turned off on mac — the CLI cleans up rotated old rollouts, measured 120s probe showed rollout directory du **net change is negative**, negative file growth would raise the cleaning stream in reverse (instead of deducting). mac's `tracked_files_total` is always 0.
- **mac process identification cannot use proc_pidpath**: the CLI process is forked from Electron Helper, `proc_pidpath` returns `.../ZCode Helper` (same path as other Helper processes, cannot distinguish); what `ps` shows as "zcode-cli" is p_comm. Correct approach: scan for a standalone NUL-terminated string matching `zcode-cli` in the `KERN_PROCARGS2` packed region (note there are **alignment NUL paddings** after argv[0], cannot parse by nargs consecutively, otherwise you get a bunch of empty strings). A previous version implemented basename matching; dump smoke test `live available=false`.
- **FFI offset misalignment must be guarded with offset_of! compile-time assertions**: the `rusage_info_v4` struct mirror of `proc_pidrusage` must be field-by-field cross-checked against SDK `sys/resource.h`, and use `offset_of!` to assert `ri_proc_start_abstime`=80, `ri_diskio_byteswritten`=152 (newer kernel layouts added `ri_proc_exit_abstime` after start_abstime; the old-layout memory was 144 — this is the pitfall). If the assertion fails you must fix the struct layout, **deleting the assertion is forbidden**; also `#[link(name = "proc")]` (the library file is libproc.dylib, the link name does not carry the lib prefix; writing "libproc" gives `ld: library not found for -llibproc`).
- **mac disk write bytes are page-cache async-flush counts, calibration must delay with grace period**: `ri_diskio_byteswritten` counts bytes of dirty pages actually written to disk, lagging `write()` by seconds to tens of seconds. Three pieces of evidence from the 2026-09-17 truth reconciliation (6 cal events, when attribution is correct pred_tps matches true_tps exactly 62.1=62.1): a 34s invocation [start, completed] window only integrated half the bytes, sample 186 was low and polluted the median on enqueue; a 1s small invocation saw 750KB appear from nowhere — the previous invocation's dirty pages only flushed at that moment; a 117s long invocation had 96% of bytes fall outside the window, the user watched 0.7 t/s for two minutes while truth was 65.3. Guards: `CleanParams.cal_grace_ms` (mac 15s / Windows 0 for in-tick processing) — pending calibration waits for the full grace period before integrating, calibration integral and raw statistic window upper limit extended to completed+grace (numerator and denominator use the same basis, pred denominator still uses real gen_ms); `cal_outlier_ratio` (mac 3x / Windows 0 disabled) rejects half-baked samples deviating beyond multiple from the active coefficient; CalEvent records `attr_pid`/`top_pid` for attribution anomaly location (when clean<<raw occasionally under multi-process concurrency, check whether the two are misaligned). Same-source lesson: mac coefficient prior was once set to 2000 based on a 120s probe (misjudged as ~3900 B/token); truth reconciliation showed ~650 (accepted samples 614/724), cold-start 3x underestimation — now set to 700.
- **Dock/Cmd+Tab and quit upstream limitations**: on Tauri/macOS a borderless-window app retains its Dock icon, and `hide()` cannot fully "hide" an Accessory app; this project adopts **Accessory mode** (`set_activation_policy`, called as early as possible in setup) + custom menu intercepting `Cmd+Q` (menu contains no `PredefinedMenuItem::quit`) + `RunEvent::ExitRequested { code: None }` fallback with `prevent_exit`. Only the combination of all three defences ensures "the only real quit paths are tray quit and floating-window right-click quit" — doing only one or two still lets the user quit from the system menu/shortcuts, after which the menu bar entry disappears and the experience is equivalent to "the app is gone".

## 11. SQLite WAL locks and long-running stability design

- **busy_timeout and read-only optimization**: Engine opening `db.sqlite` must enable `OpenFlags::SQLITE_OPEN_NO_MUTEX`, and connection initialization must set `busy_timeout(3000ms)` and enable `PRAGMA query_only = ON;`. Otherwise when ZCode CLI does high-frequency write transactions or checkpoints, the read connection immediately reports `database is locked (SQLITE_BUSY)` and drops the tick.
- **Process scan buffer zero allocation**: macOS `KERN_PROCARGS2` must reuse a scratch buffer (64KB); allocating inside the PID loop is forbidden, to avoid 64MB heap allocation spikes on every refresh.
- **session_pid reaped with process lifetime**: the session-PID mapping maintained by liveio must call `session_pid.retain` to clean up when polling detects process exit, preventing dirty data accumulation and PID-reuse misattribution over long multi-session runs.

## 12. Window control platform-native and multi-monitor safe maximize (macOS secondary display anti-jump)

- **Appearance native**: macOS's signature red-yellow-green traffic lights sit at the far left of the top bar (left to right: red `#ff5f56` collapse floating window, yellow `#ffbd2e` minimize, green `#27c93f` maximize), revealing tiny symbols on hover (`✕`, `—`, `▢`); Windows keeps the right-side `— ▢ ✕` custom-drawn buttons unchanged. The frontend injects `platform-mac` class on `body` via `navigator.userAgent.includes("Mac")`.
- **Secondary-display maximize anti-jump (`toggle_maximize_safe`)**: a borderless window (`decorations:false`) on macOS calling the system `toggleMaximize()` directly forcibly jumps back to the main display due to the system `zoom:` action. Solution is Rust-side `toggle_maximize_safe`: get the display containing the window center point (`monitor_from_point`), fill that display by its physical dimensions (reserving top system menu bar 28pt avoidance height `(28.0 * scale) as i32`), and temporarily store the pre-maximize physical rect in `AppState.saved_max_rect`; restore on next trigger or double-click on the top bar; clear the temporary store when switching to floating window (`switch_mode(Mode::Float)`) to keep state clean.
- **DOM `dblclick` is mutually exclusive with `startDragging` (2026-09-28 incident: floating-window double-click restore silently broken for two weeks after launch)**: enableDrag calls `startDragging()` on mousedown; on Windows this enters the native drag loop which swallows the mouse sequence — mouseup is only re-dispatched by tao at `WM_EXITSIZEMOVE` — so two complete click pairs never line up and DOM `dblclick` never fires (the gauge/capsule double-click restore shipped on 9-17 therefore never worked; it was only exposed when the pet double-click was added). Double-click-style interactions must follow the Tauri kernel `drag.js` approach: handle the mousedown with `e.detail>=2` and call the command directly (the kernel's drag-region double-click maximize is exactly detail 2 → `internal_toggle_maximize`; this project's floating window is detail ≥2 → `set_mode full`), and that branch also skips startDragging. The click counter increments per mousedown and does not depend on the previous mouseup having been dispatched, so detail===2 still arrives reliably after a drag loop (the kernel's double-click maximize relies on this).

## 13. In-app updates: CI artifact names ARE the matching protocol, and failure is silent

- **Artifact name is protocol**: `updater::pick_asset` matches this platform's installer by Release asset name suffix: `*_x64-setup.exe` (win-x64, portable edition does not participate in auto-install), `*_x64.dmg` (mac-x64), `*_aarch64.dmg` (mac-aarch64). Changing artifact naming or adding a new architecture without syncing `pick_asset` has **silent** consequences — the check returns normally but the installer cannot be found, the user never receives updates and there is no error (the update module by design would rather miss than disturb, see updater.rs module comment). Renaming/adding architectures must sync `asset_picking` tests in the same commit.
- **Version number synced in three places**: `tauri.conf.json` (runtime authority: `package_info().version` used for display and comparison), `Cargo.toml`, `package.json`. Missing a `tauri.conf.json` bump at release time makes the new Release's tag equal to the old version number -> judged "already latest", the update function is equally silently broken.
- **GitHub API requires User-Agent** (rejected without one); 403 rate-limiting and network disconnection are both treated as "no update". HTTP client is ureq (synchronous blocking + rustls, no OpenSSL, mac cross-build friendly), all network operations run in background threads, failures do not touch the UI.

## 14. Multi-task concurrency real-time pipeline: single-select sessions, attribution blind spots/flips, summation basis — all pitfalls

When multiple CLI processes run concurrently (multi-window, sub-agents in parallel), the real-time pipeline once had four silent gaps (identified 2026-09-18, evidence is that day's debuglog: main/sub-agent invocation blocks, attr_pid flipping, bpt swinging 262~764):

- **Gate single-select**: `inflight_from_rows` previously only took **one** session of the "latest unfinished rows" (`max_by_key`), so other concurrent tasks' traffic did not enter the reading — user perception: "sub-agent not counted / can't distinguish multiple tasks".
- **Attribution blind spot**: session->process attribution is only established when the first invocation completes (top-writer + raw>20KB). For new sessions (including a sub-agent's first invocation), before attribution is established, display falls back to the process of the "most recently completed invocation's session" — in multi-window scenarios that is **another window's** speed.
- **Attribution flip pollutes coefficient**: attribution updates per-invocation-window top-writer; when two windows stream concurrently it flips per invocation (observed: same session's two adjacent invocations attributed between two pids, the coefficient is polluted by the other window's bytes, readings deviate 2-3x).
- **Summation branch double distortion** (existing bug): full-process summation previously subtracted tracked file growth **once per process** (N-fold over-deduction), and also summed the **wall-clock durations** of each process's integral (rate diluted into a cross-process average rather than total throughput; when one process streams and another idles the reading is directly halved).

Current solution and guards (required reading before changing concurrency-related code):

- Gate returns **all** in-progress sessions (`inflight_from_rows` pure-function test guards); display process set = union of attributed pids, any session without attribution -> None = full-process summation fallback (`pick_pid_set` pure-function test guards, must not miss new processes without attribution yet).
- Aggregation stream `merge_streams`: per-tick byte summation, **wall-clock duration counted only once, tracked file growth deducted only once**; single-stream input is byte-for-byte equivalent to the historical "per-row deduct file" arithmetic (guarded by `merge_streams_deducts_file_growth_once_and_counts_secs_once`). Calibration integral goes through the same aggregation stream (key-rules #3 same-source principle extended to multi-process).
- Attribution switch hysteresis `should_reattribute` (once attributed, candidate process window bytes >= 2x current attribution before switching, test guarded); **attribution dedup `pick_attribution`** (2026-09-18 second incident: the same ZCode window opening a new task reuses the **same app-server process**, only cross-project gets a separate process — under concurrency ties, `max_by` top selection depends on HashMap iteration order, after two sessions crowd onto the same pid the display set collapses to a single process and tasks get stuck. Fix: on first attribution, if the top is already occupied by another in-progress session and the second-highest bytes reach half of top (`ATTR_DEDUP_RATIO=0.5`, concurrent stream ~1 vs idle process noise ~0.1), attribute to the second-highest instead; when current attribution is occupied, switch hysteresis is relaxed to half. Tests `pick_attribution_dedup_on_tie` / `pick_attribution_relaxed_switch_when_owned` guard); calibration sample cross-process guard `cross_pid_ok` (reject when other-window bytes > 20% of the base process — base = attributing process; **the no-attribution full-process summation branch uses the top process as base, that branch's integral also mixes in other-window bytes, cannot be allowed**; cal log `others_kb` diagnosis); `cal_sample`'s clean/raw guard numerator/denominator are **paired** (when clean comes from the attributing process, raw also uses the attributing process's).
- **Same-process multi-session summed honestly**: multiple sessions carried by the same app-server process (new task in same window) are not separable at the byte level — task row counts as one row, `n_sessions` marks session count into the task total (frontend triggers display by Σ sessions >= 2), speed is that process's total. For multi-task issues directly look at the tick log's `pids` (KB/s probe per tracked process) / `infl` (in-progress session count) / `attr` (session->pid mapping) trio, do not only look at npids.
- Round drift only ingests **single-process rounds** (main.rs `round_tps` third field records saw_multi, any measured tick with npids>1 skips the whole round; npids = count of processes whose contribution reaches streaming magnitude in the window, idle process base-noise leakage does not count) — throughput differences from task-count changes are not coefficient drift; 1 task at 40 t/s and 3 tasks at 120 t/s share the same coefficient; false triggers reset a good coefficient back to the prior.

## 15. Platform primitive limits for network bytes: no public primitive for direct per-process measurement, basis must be tiered

Background: netio was originally built to distinguish ZCode session/non-session uploads (2026-09-17 ZCode was found silently uploading full-repo snapshots to Aliyun OSS; that feature was later discontinued by ZCode, and netio's snapshot-artifact monitoring layer and snapshot guard card were removed along with it on 2026-09-28 — but this rule's platform-primitive conclusions still hold and constrain any new basis in netio/liveio):

- **Winsock sent/received bytes do not enter any process IO counter**: during a 20MB curl download `ReadTransferCount` was only 7.8KB (`Write` 12MB was all disk-mirror writes to the NUL device, `Other` 82KB was miscellaneous IOCTL). => ① liveio's `WriteTransferCount` streaming speed measurement is **naturally immune to network pollution**, do not add network semantics to it; ② trying to reverse-derive network bytes from IO counters is a dead end. The old documentation's interpretation of a ">100KB write burst at invocation start" as "request-body upload" was a misjudgment — it is actually the disk flush of the prompt text writing message rows/rollouts.
- **TCP ESTATS is broken (2026-09-18 second verification archived as `scripts/estats_probe.py`, do not retry from scratch)**: `SetPerTcpConnectionEStats`/`GetPerTcpConnectionEStats` (note the **export name has EStats with capital S**, different from the MSDN doc name Estat; direct `#[link]` gives LNK2019, must use LoadLibrary+GetProcAddress). First verification (code not archived): all connections including this process's own returned `ERROR_NOT_SUPPORTED`(50), even as admin. Second verification (build 26200, normal privileges): all 4 v4/v6 export symbols exist; `Set` (enable Data collection) returns `ERROR_ACCESS_DENIED`(5) for **both own and other processes' connections** — enabling collection is a privileged operation independent of connection ownership; `Get` when not enabled always fails (mostly `ERROR_INVALID_USER_BUFFER`(1784), some connections 50), changing call style (Get with Rw buffer / Set with Rod buffer) does not change the result. => The only public per-connection byte-count API is unavailable under normal privileges (the panel does not assume admin), **true per-process network speed is therefore not implementable**, only estimation bases are available (whole-machine truth + session token estimation, two tiers).
- **ETW kernel network events require admin**, desktop tools cannot rely on them.
- **Windows interface counters (`GetIfTable` dwIn/dwOutOctets) are 32-bit**: must apply **per-interface** modulo 2^32 differencing — each interface wraps at a different time, summing first then differencing is wrong after any interface wraps (the initial implementation had this bug, caught by tests). mac `getifaddrs` ifi_*bytes are 64-bit, but **each interface returns multiple rows by address family, must dedup by interface name** otherwise bytes are doubled.
- **Cache-hit prompts are not re-sent**: under 98% hit rate the whole machine's daily upload is only tens of KB — the numerator for session upload estimation must use `input - cache_read` (uncached portion); estimating by full re-send inflates tens of times. Measured session download density ~731 B/token (whole-machine including misc stream upper bound) / UI pipeline bpt~320 (lower bound), estimation coefficient set to 400.
- **"Doesn't match Task Manager" is a basis difference, not a counting bug** (user reported once on 2026-09-18): (1) units — Task Manager is in bits (Mbps/Kbps), panel is in bytes, x8 for comparability; (2) scope — Task Manager Wi-Fi page only covers the selected adapter, panel sums all non-loopback interfaces (virtual NIC/VPN tunnel traffic counted on both inner and outer layers); (3) time — panel is ~1s sliding window average (`NET_WINDOW_MS`, aligned with Task Manager refresh cadence), bursts are flattened and sampling instants differ. Additionally: whole-machine daily cumulative only covers the panel's active period (baseline resets on restart).

=> Current solution (netio.rs): whole-machine interface counts (real) + session token estimation (≈) two-tier layering, UI annotates basis per item; connection attribution uses `GetExtendedTcpTable`(OWNER_PID) grouped by process (command line containing `zcode.cjs` = session group, rest `zcode.exe` = desktop non-session group). Guard tests: `wrap_delta_handles_32bit_wrap_and_resets` (wrap/reset clamps to 0), `sess_est_scales_with_tokens` (estimation coefficient contract).

## 16. mac window fullscreen/Dock: only trust official identity and default behavior, don't fight AppKit details (2026-09-19 fullscreen deep-dive conclusion)

User requested mac green traffic light be native fullscreen. The breakthrough process and lessons (multiple rounds of real testing within one day):

- **Accessory (menu-bar resident) app windows can never get native Space fullscreen** — the green button only gives secondary fullscreen (fills screen but menu bar does not hide). `collectionBehavior=FullScreenPrimary`, making the window opaque, runtime-binding `toggleFullScreen:` are all ineffective. **The only solution = Regular app identity**: full panel `set_activation_policy(Regular)` (bright Dock icon) + native Overlay title bar, the green button is native fullscreen; collapsing the floating window switches back to Accessory (hides Dock, app does not exit); dynamic switching between the two states is implemented.
- **Bare objc FFI three pitfalls**: (1) Cocoa property getters have no `get` prefix (`collectionBehavior`; writing `getCollectionBehavior` -> unrecognized selector -> **ObjC exception crosses Rust extern "C" and directly aborts the process**, and the first-crash panic info is swallowed; you need lldb to break on `panic_cannot_unwind` or read `lastExceptionBacktrace` in `~/Library/Logs/DiagnosticReports/*.ips` to locate); (2) declaring multiple different signatures for the same `#[link_name="objc_msgSend"]` produces warnings and hidden danger; fn pointer transmute has runtime checks on newer rustc; (3) creating an ObjC class at runtime for button target/action, then calling tauri window API + `setPresentationOptions:` inside the callback throws NSException and crashes (the custom "immersive fullscreen" approach was abandoned for this reason; code has been stripped). **Conclusion: interacting with AppKit only uses tauri public API; capabilities the official API lacks (native fullscreen) are solved by switching app identity, not force-built.**
- **Window experiments must be instantly revertible**: multiple uncommitted experimental groups this round relied on `git stash` to one-click return to the verified state; "after changing, start dev first to let the user see the effect, only build/push after confirmation" is the fixed process (explicit user request).
